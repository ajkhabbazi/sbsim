# 해석해 vs 유한차분 — 속도 비교

## 한눈에 보기

- **해석해(직접 풀이)가 유한차분(반복 풀이)보다 빠르고, 정확하다.** 실제 건물 기준 처음 1스텝은 약 1.9배, 이후 매 스텝은 약
    1.25배 빠르다. 게다가 유한차분은 "수렴했다"고 선언한 뒤에도 정답과 0.05 K 차이가 남는다.
- **해석해를 텐서 연산으로 바꿔도 더 빨라지지 않는다.** 이미 전체 시간의 0.6%만 차지하는 부분이라서, 그 부분을 아무리 손봐도 전체
    체감 속도는 그대로다.
- **GPU를 실제로 설치해서 돌려봤는데, 지금 규모(276칸)에서는 오히려 2~3배 느려진다.** 격자를 훨씬 키우면(1만 칸 이상)
    GPU가 유리해지는 지점이 오긴 하지만, 그 지점에서도 지금 쓰는 CPU 방식(희소 행렬)을 못 이긴다. GPU가 실제로 이기는 경우는
    딱 하나, "여러 건물을 동시에 풀 때"뿐이다. (아래 5절)

측정 기기: AMD Ryzen 7 5800X (8코어), NVIDIA GeForce RTX 3080 10GB (WSL, 드라이버 595.95),
TensorFlow 2.15.1, SciPy 1.15.3. 실제 건물 벤치마크는 테스트에 쓰는 건물(격자 23×12 = 제어체적 276개, 복사
표면 146개)로 `use_analytical_solution` 옵션을 켜고/끄고 **연속 100 스텝**을 돌려 측정했다.

## 1. 무엇을 비교하는 것인가

한 타임스텝마다 아래 연립방정식을 푼다. 미지수는 제어체적(building의 각 칸) 276개의 온도다.

```
A · T = b
```

- `A` : 276×276 행렬. 대각선은 "이 칸의 열용량 + 이웃/외기로 빠져나가는 전도·대류량", 비대각선은 "이웃 칸과 연결되는
    컨덕턴스(열이 얼마나 잘 통하는가)"다. 한 칸은 최대 4개 이웃과만 연결되므로 대부분의 칸이 0인 **희소(sparse) 행렬**이다.
- `b` : 직전 스텝 온도 × 열용량 + HVAC 열량 + 복사 열량 + 외기 온도 항.

이 방정식을 푸는 방법은 크게 두 갈래로 나뉜다.

| 갈래                         | 뜻                                                             | 결과                                                                 |
| ---------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------- |
| **반복법 (유한차분식 풀이)** | 온도를 대충 찍어놓고, 방정식을 만족하도록 조금씩 계속 고쳐나감 | 반복을 멈춘 시점까지의 **근사값** (정답과 항상 약간의 오차가 남는다) |
| **직접법 (해석해)**          | 행렬을 한 번 분해해서 정확히 역산                              | 부동소수점 반올림 오차 수준의 **정확값**                             |

> **"해석해"라는 표현에 대해** — 종이에 손으로 쓰는 닫힌 형태의 공식이라는 뜻이 아니다. **반복 없이 행렬을 한 번에 정확히
> 푼다**는 뜻으로 쓴다. 두 방법 모두 같은 격자에서 나온 같은 연립방정식 `A·T = b`를 푸는 것이고, 차이는 그걸 반복으로 근사하느냐
> 한 번에 정확히 계산하느냐일 뿐이다.

## 2. 방법별로 뭘 하는 건지, 어느 갈래인지

먼저 분류표:

| 방법               | 갈래            | 한 줄 설명                                                      |
| ------------------ | --------------- | --------------------------------------------------------------- |
| 야코비 점 완화법   | 반복 (유한차분) | 이웃의 직전 값으로 내 값을 다시 계산, 모든 칸을 동시에 반복     |
| 가우스–자이델법    | 반복 (유한차분) | 야코비와 같지만 이웃의 최신 값을 바로 사용, 순서대로 반복       |
| 켤레기울기법       | 반복 (유한차분) | 매 회차 최적 방향을 골라 이동, 야코비보다 훨씬 적은 회차로 수렴 |
| SciPy `spsolve`    | 직접 (해석해)   | 희소 행렬 LU 분해, 호출할 때마다 분해를 다시 함                 |
| SciPy `splu` 캐시  | 직접 (해석해)   | 위와 같은 LU 분해, 분해 결과를 저장해서 재사용                  |
| TF 밀집 LU 분해    | 직접 (해석해)   | 같은 분해를 0을 포함한 꽉 찬 행렬로, TensorFlow로 실행          |
| TF 밀집 역행렬     | 직접 (해석해)   | 역행렬을 미리 구해두고 매번 행렬×벡터 곱만 실행                 |
| 밀집 촐레스키 분해 | 직접 (해석해)   | 행렬이 대칭일 때 쓰는 LU의 절반 연산량 버전                     |

### 반복법(유한차분) 계열 — 왜 느리고 왜 부정확한가

모두 같은 `A·T = b`를 **반복해서 근사**한다. 정답에 다가갈 뿐 도달하지는 않는다.

- **야코비 점 완화법 (Jacobi point relaxation)** — *현재 `tf_simulator.py`의 기본값*. 각 칸에 대해
    "이웃들의 **직전 회차** 온도를 그대로 믿고, 내 온도만 에너지 균형이 맞도록 다시 계산한다"를 모든 칸에 동시에 적용한다. 한 번
    다 훑는 것을 1 sweep이라 하고, 온도 변화가 임계값 아래로 떨어질 때까지 반복한다. 모든 칸을 동시에 갱신하므로 텐서 연산 한
    줄로 표현되어 병렬화는 쉽지만, 열 정보가 격자를 한 칸씩만 타고 퍼지므로 수렴이 느리다.
- **가우스–자이델법 (Gauss–Seidel)** — *`simulator.py`가 쓰는 방식*. 야코비와 똑같은데 이웃 값을 직전 회차가
    아니라 **이번 회차에 이미 갱신된 값**으로 쓴다. 그래서 야코비보다 대략 2배 빨리 수렴하지만, 칸을 순서대로 처리해야 해서 텐서 한
    방으로 병렬화할 수 없다.
- **켤레기울기법 (conjugate gradient)** — 행렬이 대칭이고 양의 정부호일 때 쓰는 반복법. 야코비처럼 "한 칸씩" 퍼뜨리는
    게 아니라, 매 회차마다 지금까지 탐색한 방향과 겹치지 않는 새 방향을 골라 그쪽으로 최적 거리만큼 이동한다. 그래서 야코비보다 훨씬
    적은 회차로 수렴한다. (이 문서의 이전 판에서 설명 없이 "CG"라고만 썼던 것이 바로 이것이다.)

### 직접법(해석해) 계열 — 모두 같은 답, 차이는 속도뿐

아래 네 가지는 **완전히 같은 정확한 답**을 낸다. 실제로 측정해도 서로 간 차이는 **정확히 0.000 K**다.

- **SciPy `spsolve`** — *현재 `use_analytical_solution=True`일 때 쓰는 것*. 희소 행렬을 LU
    분해(`A = L·U`, 아래삼각 × 위삼각)한 뒤 대입으로 푼다. 호출할 때마다 **분해부터 다시 한다.**
- **SciPy `splu` 캐시** — 같은 LU 분해인데 **분해 결과를 저장해두고 재사용**한다. 한 타임스텝 안에서
    복사(radiation) 항 때문에 평균 2.8번 다시 푸는데, 행렬 `A` 자체는 그 사이 안 변하므로 분해는 1번만 하면 된다.
    순수한 중복 제거다.
- **TF 밀집 LU 분해** — 같은 LU 분해를 희소가 아니라 **꽉 찬(dense) 276×276 텐서**로 하고 TensorFlow로
    실행한다. "텐서로 하면 빠를까?"를 직접 실험한 것. 원래 행렬은 0이 아닌 칸이 약 1,300개뿐인데, 밀집으로 하면 76,176칸을
    전부 계산하게 된다.
- **TF 밀집 역행렬 + 행렬곱** — `A⁻¹`을 한 번 구해서 저장해두고, 매번 `T = A⁻¹ · b` 행렬-벡터 곱만 한다. 분해보다
    풀이 단계가 단순해서 GPU에 가장 유리한 형태다.
- **밀집 촐레스키 분해** — 대칭 양정부호 행렬에만 되는 LU의 특수판, `A = L·Lᵀ`. 연산량이 LU의 절반이다. (이번 열 수지
    수정에서 접촉 면적을 `min(w_P, w_N)`로 통일해 행렬이 대칭이 된 덕분에 이 방법이 가능해졌다.)

## 3. 결과 — 얼마나 빠른가, 첫 스텝만인가 계속인가

실제 건물, 연속 100 스텝, CPU:

| 방법                          | 갈래 | 1스텝째      | 이후 평균        | 정확도 (spsolve 대비) |
| ----------------------------- | ---- | ------------ | ---------------- | --------------------- |
| 야코비 반복 (현재 기본)       | 반복 | 25.7 ms      | 17.2 ms          | **0.05 K 틀림**       |
| SciPy `spsolve` (현재 해석해) | 직접 | 12–14 ms     | 14.0 ms          | 기준                  |
| SciPy `splu` 캐시             | 직접 | 10–11 ms     | **13.2–13.9 ms** | 0.000 K               |
| TF 밀집 LU (텐서)             | 직접 | 16.6–18.0 ms | 16.0–16.3 ms     | 0.000 K               |
| TF 밀집 역행렬 (텐서)         | 직접 | 16.2–16.3 ms | 14.4–14.6 ms     | 0.000 K               |

(두 번 재실행해 값 범위로 표기했으며, 어느 쪽이든 결론은 동일하다.)

**정리하면:**

- 해석해가 첫 스텝은 **약 1.9배**, 이후 매 스텝은 **약 1.25배** 빠르다. 즉 둘 다에서 이기지만, 첫 스텝에서 격차가 더
    크다.
- 이유: 첫 스텝은 초기 온도(292 K 균일)가 정답에서 멀어 야코비가 수십~수백 sweep을 돌아야 한다. 두 번째 스텝부터는 직전 스텝
    답에서 시작하므로(warm start) 답이 거의 안 변해 2~3 sweep 만에 임계값을 통과한다.
- 하지만 "빨리 통과한다"와 "맞다"는 다른 이야기다. 야코비는 임계값을 통과했을 뿐 정답에서 **0.05 K** 떨어져 있고, 이 오차가
    스텝마다 반복적으로 남는다. 해석해는 매 스텝 정확한 답을 준다.

## 4. 해석해를 텐서로 하면 더 빨라지나 — 아니다

|                                     | CPU 1스텝    | CPU 이후 평균                |
| ----------------------------------- | ------------ | ---------------------------- |
| SciPy `splu` 캐시 (희소, 텐서 아님) | 10–11 ms     | **13.2–13.9 ms** ← 가장 빠름 |
| TF 밀집 역행렬 (텐서)               | 16.2–16.3 ms | 14.4–14.6 ms                 |
| TF 밀집 LU (텐서)                   | 16.6–18.0 ms | 16.0–16.3 ms                 |

이유는 **선형 풀이가 한 스텝 전체 시간에서 차지하는 비중이 거의 없기 때문**이다. 한 스텝(약 13~14 ms) 안에서 시간이 어떻게
쓰이는지 뜯어보면:

| 구간                                                             | 시간                              | 비중        |
| ---------------------------------------------------------------- | --------------------------------- | ----------- |
| 행렬 조립 (`A`, `b` 만들기)                                      | 0.31~0.37 ms × 2.8회 ≈ 1.0 ms     | 약 7%       |
| **선형 풀이 (splu 캐시)**                                        | **0.03~0.04 ms × 2.8회 ≈ 0.1 ms** | **약 0.6%** |
| 나머지 (분자·분모 텐서 구성, 복사 계산, 외기 컨덕턴스 재계산 등) | 약 12~13 ms                       | 약 92%      |

전체의 0.6%만 차지하는 부분을 아무리 최적화해도 체감 속도는 그대로다. 오히려 텐서로 바꾸면 276×276 꽉 찬 행렬(0이 아닌 칸은
1,300개뿐)을 통째로 계산하게 되고 TensorFlow 호출 자체의 오버헤드까지 붙어서 순손해가 난다.

참고로 이 92%를 차지하는 부분 중 눈에 띄는 낭비가 하나 있다:
`get_oriented_ambient_ conductance_tensors`(외기와 맞닿은 면의 컨덕턴스 계산)가 **매 반복마다 다시
계산**되며 혼자 전체 시간의 25%를 먹는다. 이웃 칸끼리의 면 컨덕턴스는 이미 `__init__`으로 빼놨는데 외기 쪽만 빠져있다. 이걸
옮기는 게 텐서 풀이보다 훨씬 큰 이득이다 (이번 작업 범위 밖이라 여기서는 손대지 않았다).

## 5. GPU 실제 설치 후 재측정

`.venv`에 `tensorflow[and-cuda]==2.15.1`을 설치해 RTX 3080을 인식시킨 뒤
(`tf.config.list_physical_devices('GPU')` → `[GPU:0]`, compute capability 8.6
확인) 아래 세 가지를 다시 측정했다. 재현성 확인을 위해 각 실험을 **두 번씩** 돌렸고 결과는 매번 오차범위 안에서 일치했다.

### 5-1. 실제 건물(276칸)에서는 GPU가 오히려 느리다

| 방법                  | CPU 이후 평균 | GPU 이후 평균 | GPU 배율            |
| --------------------- | ------------- | ------------- | ------------------- |
| 야코비 반복           | 17.2~17.5 ms  | 41.1~41.8 ms  | **약 2.4배 느림**   |
| SciPy `spsolve`       | 14.0 ms       | 41.9~47.9 ms  | 약 3~3.4배 느림\*   |
| SciPy `splu` 캐시     | 13.2~13.9 ms  | 42.1~46.7 ms  | 약 3.2~3.5배 느림\* |
| TF 밀집 LU (텐서)     | 16.0~16.3 ms  | 56.8~64.1 ms  | 약 3.5~3.9배 느림   |
| TF 밀집 역행렬 (텐서) | 14.4~14.6 ms  | 34.7~47.5 ms  | 약 2.4~3.3배 느림   |

\* SciPy로 푸는 부분 자체는 여전히 CPU에서 도는데도 전체가 느려졌다. 시뮬레이터의 나머지 TensorFlow 연산(분자/분모 텐서
구성 등)이 GPU가 있으면 자동으로 GPU로 옮겨가기 때문이다.

**왜 느려지나**: 276개짜리 작은 텐서 하나를 GPU로 보내고, 계산하고, 다시 받아오는 데 드는 고정 비용(커널 실행 + 메모리 전송,
건당 수십 µs)이 실제 계산량(칸 276개짜리 덧셈)보다 훨씬 크다. 시뮬레이터는 이런 작은 연산을 한 스텝에 수백 번 하므로 이 고정 비용만
계속 쌓인다. **GPU는 큰 계산 하나를 할 때 유리하지, 작은 계산을 아주 많이 반복할 때는 불리하다.**

### 5-2. 격자를 얼마나 키워야 GPU가 유리해지나

같은 물성·같은 구조로 격자만 키워서, 선형 풀이 부분만 따로 떼어 측정했다 (float32 기준, 두 번 재실행해 일치 확인):

| 제어체적 수     | CPU 희소 `splu` 풀이 (지금 방식) | CPU 밀집 역행렬×벡터                      | GPU 밀집 역행렬×벡터 | CPU 밀집 촐레스키 분해 | GPU 밀집 촐레스키 분해 |
| --------------- | -------------------------------- | ----------------------------------------- | -------------------- | ---------------------- | ---------------------- |
| 289 (지금 규모) | **0.011~0.012 ms**               | 0.29~0.30 ms                              | 0.34~0.37 ms         | 8.5~10.9 ms            | 28.7~34.0 ms           |
| 1,024           | **0.047~0.048 ms**               | 0.34~0.35 ms                              | 0.35~0.38 ms         | 21.7 ms                | 5.8~11.2 ms            |
| 4,096           | **0.22 ms**                      | 1.92~1.96 ms                              | 0.42~0.45 ms         | 562~565 ms             | 40~51 ms               |
| 10,000          | **0.58~0.59 ms**                 | 11.4~12.9 ms                              | 0.85~7.8 ms          | 4,870~5,054 ms         | 380~382 ms             |
| 25,600          | 문제없이 실행됨                  | **CPU 자체가 10분 넘게 끝나지 않아 중단** | 시도 불가            | —                      | —                      |

읽는 법:

1. **GPU가 CPU 밀집 계산을 이기기 시작하는 건 제어체적 4,000개쯤부터**다. 1만 개 에서는 최대 15배까지 벌어진다. GPU
    자체는 제 역할을 한다.
2. **그런데 그 지점에서도 지금 쓰고 있는 CPU 희소 `splu`가 여전히 가장 빠르다.** 1만 개에서 CPU 희소 0.58 ms인데,
    같은 크기를 GPU 밀집으로 풀어도 최소 0.85 ms다. 희소 행렬은 0이 아닌 칸 약 5만 개만 계산하는 반면 밀집은 1억 칸을
    계산하기 때문에, GPU가 아무리 빨라도 이 차이를 못 뒤집는다.
3. **2만 5,600개로 더 키우자 CPU에서 밀집 역행렬을 구하는 것 자체가 10분을 넘겨도 끝나지 않아 중단시켰다.** (25,600²
    × 8바이트 ≈ 5.2 GB짜리 행렬을 역산하는 계산 량은 대략 N³에 비례해서, 1만 개 대비 17배 커진 크기가 그대로 시간에
    반영된다.) 반면 희소 방식은 같은 크기에서 여전히 1 ms 이내로 끝난다. 밀집 방식은 GPU를 쓰든 안 쓰든 이 크기부터는 이미
    비현실적이라는 뜻이다.

**결론: 이 문제에서 GPU로 이득을 보려면 행렬을 밀집 형태로 바꿔야 하는데, 밀집으로 바꾸는 순간의 손해가 GPU로 얻는 이득보다 크다.
지금 쓰는 CPU 희소 방식이 어느 크기에서든 가장 낫다.**

### 5-3. GPU가 실제로 이기는 유일한 경우 — 여러 건물을 동시에 풀 때

같은 행렬을 서로 다른 우변 `b` 여러 개에 대해 **한꺼번에** 풀면(예: 건물 512채를 병렬 시뮬레이션하거나, 강화학습 환경 512개를
동시에 돌릴 때) GPU가 건당 고정 비용을 나눠 갖게 되어 유리해진다. 제어체적 289개 기준, 시스템 1개당 걸리는 시간:

| 동시에 푸는 개수 | CPU          | GPU            |
| ---------------- | ------------ | -------------- |
| 1개              | 0.29~0.30 ms | 0.34~0.37 ms   |
| 64개             | 6.5~7.6 µs   | 6.4~6.6 µs     |
| 512개            | 2.3~4.3 µs   | **1.0~1.1 µs** |

512개를 동시에 돌리면 GPU가 CPU보다 약 2~4배, 1개씩 따로 돌리는 것보다 최대 **300배 이상** 빠르다. 즉 GPU는 "건물
하나를 빨리 풀 때"가 아니라 "여러 건물을 동시에 풀 때"만 의미가 있다.

## 6. 결론과 권장 조치

1. **지금 쓰는 해석해(`spsolve`)가 유한차분(야코비)보다 이미 더 빠르고 정확하다.** 추가 조치 없이도 유지할 이유가 충분하다.
2. **선형 풀이 부분(전체의 0.6%)을 텐서나 GPU로 바꾸는 건 효과가 없다.** 오히려 지금 규모(276칸)에서 GPU는 2~3배
    손해다. 격자를 1만 칸 이상으로 크게 키우기 전에는 건드릴 이유가 없다.
3. **실제로 효과가 있는 개선은 따로 있고, 둘 다 작은 수정이다.**
    - `spsolve` → `splu` 캐시로 바꿔서, 한 스텝 안에서 반복되는 2.8회의 중복 분해를 1회로 줄인다.
    - `get_oriented_ambient_conductance_tensors`를 (면 컨덕턴스처럼) `__init__`으로 옮겨서 매
        반복 재계산을 없앤다 — 전체 시간의 25%를 차지하는 부분이다. 이 문서의 범위에서는 실제 코드 수정은 하지 않았고, 측정만 해서
        근거를 정리했다.
4. **GPU를 의미 있게 쓰려면 "한 건물을 빨리"가 아니라 "여러 건물을 동시에"로 문제를 바꿔야 한다.** 이는 지금 시뮬레이터의
    numpy ↔ TensorFlow 데이터 전달 구조를 손봐야 하는 큰 작업이라 이번 범위에는 포함하지 않았다.
